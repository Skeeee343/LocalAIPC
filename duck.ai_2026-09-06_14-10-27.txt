## Important limitation: Super Productivity is local-first

Super Productivity stores its data locally and syncs through mechanisms such as WebDAV, SuperSync, Dropbox or other supported providers. It is not fundamentally a server-side task database like Vikunja. <citation src="1,7"></citation>

That creates an architectural question:

> Which machine is the authoritative Super Productivity client?

If OpenClaw runs on a server while Super Productivity is running on your desktop or phone, a local REST API on `localhost` will not be reachable by OpenClaw. You have three options:

### Option A: Run OpenClaw and Super Productivity on the same machine

This is the simplest and most reliable option.

```text
OpenClaw ── localhost ── Super Productivity local API
```

Good for a desktop or home server where both applications are always running.

### Option B: Run a small bridge beside Super Productivity

Run the adapter on the machine where Super Productivity is active, then expose only the adapter over your private network or Tailscale.

```text
OpenClaw server ── Tailscale ── adapter ── localhost ── Super Productivity
```

This is probably the best design if OpenClaw runs on a home server but Super Productivity runs on your workstation.

### Option C: Write a Super Productivity plugin

A plugin runs inside the application and can use Super Productivity’s plugin APIs, including task operations, counters, notifications and synced plugin data. <citation src="8"></citation>

This is the strongest option if you need:

- Habit counters
- Completion hooks
- Native notifications
- Access to app state not exposed by REST

- Ollama, if you want uncomplicated GPU access
- Super Productivity, because it is a desktop application
- NVIDIA drivers and CUDA libraries

A practical arrangement is:

```text
Native:
  NVIDIA driver
  Ollama
  Super Productivity

Docker:
  OpenClaw
  MCP adapter
  Caddy, if needed
```

You can run Ollama in Docker, but native installation generally reduces GPU-passthrough complexity.

## Secrets

Do not put tokens directly in Git. Use Ansible Vault:

```bash
ansible-vault create group_vars/vault.yml
```

Example:

```yaml
openclaw_api_token: "..."
superproductivity_api_token: "..."
tailscale_auth_key: "..."
```

Reference them in templates:

```yaml
openclaw_token: "{{ openclaw_api_token }}"
```

Set restrictive permissions on generated files:

```yaml
- name: Install OpenClaw configuration
  ansible.builtin.template:
    src: openclaw-config.json.j2
    dest: /etc/openclaw/config.json
    owner: root
    group: root
    mode: "0600"
```

## Backups

Automate backups of:

- OpenClaw configuration
- MCP adapter configuration
- Super Productivity sync/data location
- Ansible Vault files, stored separately and encrypted
- Model configuration, but not necessarily model files
- Any custom plugin source

Use a systemd timer or cron job. Keep at least:

```text
7 daily backups
4 weekly backups
3 monthly backups
```

Do not rely on the model directory as a backup of your actual productivity data.

## Health checks

The playbook should finish by checking:

```bash
curl http://127.0.0.1:11434/api/tags
curl http://127.0.0.1:8787/health
curl http://127.0.0.1:3000/health
nvidia-smi
```

Also perform an actual model test:

```bash
ollama run gemma4:e2b "Return only the word OK."
```

For the MCP adapter, add an integration test such as:

```text
Create a temporary task → read it back → delete it
```

Use a test project, not your real task list.

## Recommended installation phases

Do not make the first playbook one huge destructive install. Use tags:

```bash
ansible-playbook -i inventory.ini site.yml --tags common,docker
ansible-playbook -i inventory.ini site.yml --tags ollama
ansible-playbook -i inventory.ini site.yml --tags openclaw,mcp
ansible-playbook -i inventory.ini site.yml --tags superproductivity
ansible-playbook -i inventory.ini site.yml --tags backups
```

This lets you repair one component without reinstalling everything.

## Best practical approach

I would build the automation in this order:

1. Ansible installs common packages and Docker.
2. Ansible verifies the NVIDIA driver and GPU.
3. Ansible installs Ollama and downloads Gemma 4 E2B.
4. Ansible deploys the MCP adapter.
5. Ansible deploys and configures OpenClaw.
6. You manually install and test Super Productivity.
7. Once the integration works, automate Super Productivity’s desktop installation and local API configuration.
8. Add backups and upgrade commands.

That manual step is worthwhile because Super Productivity’s desktop behavior, data location and API availability may vary by platform and release.

## Final recommendation

Use:

```text
bootstrap.sh
    └── Ansible
          ├── native Ollama
          ├── native Super Productivity
          ├── containerized OpenClaw
          ├── containerized or native MCP adapter
          ├── Gemma 4 E2B
          ├── secrets via Ansible Vault
          └── automated backups and health checks
```

A `.sh` script alone would be quicker to write, but Ansible is the better long-term choice because it gives you repeatability, idempotence, host separation, secrets handling and easier upgrades.
